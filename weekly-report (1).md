## 1. assemble.ai Evaluation – Client: Aliyan

## 2. SLA Countdown Component – Internal R&D

Identified and solved a common Salesforce Service Cloud problem on my own initiative, end-to-end, without it being assigned as a client deliverable.

**Problem:** Agents working Cases had no easy way to see how much SLA time remained, which made it hard to prioritize urgent work over lower-priority tickets.

**Solution:** Built a live, on-record countdown timer that shows remaining SLA time directly on the Case page.

**Benefit:** Agents can see SLA risk at a glance and triage their queue accordingly, reducing the chance of SLA breaches caused simply by lack of visibility.

### Implementation Details
- **Data model:** Added custom objects and custom fields to track SLA start time, due time, and breach status on Cases. `SLA_Breached__c` was deliberately kept as a formula field rather than being set imperatively, keeping breach status always in sync with current time without relying on scheduled jobs.
- **Apex layer:** Built Apex classes and a trigger to handle SLA calculation and automation. An initial validation-rule-based approach (using a VLOOKUP) didn't hold up, so this was replaced with a trigger-based Apex implementation for more reliable, testable logic. SLA hours were hardcoded per the agreed scope rather than built out as a full policy-lookup system, since the added complexity wasn't justified for the current use case.
- **LWC component:** Developed a Lightning Web Component to surface the countdown on the Case record page. An early version only reflected server-side values and didn't feel "live"; this was resolved by adding a client-side `setInterval` ticker for smooth second-by-second countdown, with a 30-second resync against the server to keep the displayed value accurate.
- **Status:** Fully built and verified working — the countdown displays correctly and updates live on Case records.

### Process Notes
- Followed a phased approach: data model → Apex business logic → LWC UI → deployment, validating each phase before moving to the next.
- Treated this as a small but complete deployable feature rather than a proof-of-concept, including handling the edge cases (live ticking, sync accuracy) that separate a demo from something usable day-to-day.
